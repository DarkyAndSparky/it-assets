# Схема данных

> Справочный документ (IDEA-6). Описывает физическую схему SQLite
> (`server/db/sqlite.js`) и логику типизированных meta-полей (PROD-1..4).
> Не автогенерируется — при изменении схемы БД или системы полей стоит
> сверить этот файл вручную.

## Основная таблица: `assets`

Один актив (единица оборудования) — одна строка. Организация/филиал/локация/
ответственный хранятся ДВОЙНО: как id-ссылка на справочник (`org_id`,
`filial_id`, `location_id`, `responsible_id`) и как текстовый снапшот имени
на момент последней записи (`org`, `filial`, `location`, `responsible`).

Зачем снапшот, если есть id: если справочную запись переименуют или закроют
(ликвидируют организацию, закроют филиал), у старых активов не должна
потеряться историческая привязка — снапшот остаётся читаемым даже без
живой ссылки. При чтении (`assets.repo.js::normalizeAsset()`) id разрешается
в АКТУАЛЬНОЕ имя, если ссылка ещё жива; иначе используется снапшот.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | TEXT PK | UUIDv7 |
| `tab` | TEXT | `os` \| `small` \| `infra` — верхнеуровневая вкладка (ноутбуки/ПК/мониторы vs мелкая техника vs инфраструктура) |
| `category` | TEXT | Категория внутри вкладки (настраивается в Настройках → Категории) |
| `type` | TEXT | Название типа устройства — свободный текст, СВЕРЯЕТСЯ ПО ИМЕНИ со справочником `type_codes` (см. ниже), не хранит `type_code` напрямую |
| `filial` / `filial_id` | TEXT | Филиал — снапшот + id (см. выше) |
| `address` | TEXT | Адрес филиала на момент записи (тоже снапшот, копируется из справочника филиалов при выборе) |
| `location` / `location_id` | TEXT | Локация внутри филиала |
| `responsible` / `responsible_id` | TEXT | Ответственный сотрудник |
| `org` / `org_id` | TEXT | Организация-владелец |
| `model`, `serial` | TEXT | Модель, серийный номер |
| `inv` | TEXT | Инвентарный номер (формат зависит от `org_inv_rules`, см. ниже) |
| `inv_prev` | TEXT | Предыдущий инв. номер (история присвоения) |
| `status` | TEXT | `используется` \| `резерв` \| `ремонт` \| `списан` (списанные скрыты из большинства выборок, но не удаляются физически) |
| `note` | TEXT | Свободный комментарий |
| `created_at`, `updated_at` | TEXT (ISO) | |
| `meta_*` (14 колонок) | TEXT | Дополнительные поля — см. "Meta-поля" ниже |

**Индексы:** `idx_assets_status`, `idx_assets_org_id` — см. примечание в конце
файла про то, реально ли они используются текущими запросами.

## Meta-поля и типизированная схема (PROD-1..4, PROD-5)

Физическое хранилище — 17 ФИКСИРОВАННЫХ колонок `meta_ip`, `meta_mac`,
`meta_subnet`, `meta_winbox`, `meta_login`, `meta_password`, `meta_cabinet`,
`meta_controller`, `meta_inv`, `meta_network`, `meta_hostname`,
`meta_cartridge`, `meta_firmware`, `meta_note2`, `meta_warranty`,
`meta_purchase_date`, `meta_cost`
(канонический список — `META_KEYS` в `server/db/sqlite.js`, отдаётся клиенту
через `GET /api/meta-keys`, чтобы не дублироваться вторым списком на
фронте). `meta_warranty` (PROD-5) и `meta_purchase_date`/`meta_cost`
(PROD-18) — три ключа, добавленных ПОСЛЕ первоначальных 14: реальный
`ALTER TABLE assets ADD COLUMN` (тем же защищённым паттерном PRAGMA
table_info + условный ALTER, что уже применялся для
`users.can_view_accounts`) — расширение сделано дважды подряд без
проблем, паттерн можно считать проверенным.

Какое подмножество этих 14 ключей показывать для конкретного типа
устройства, каким типом ввода и с каким набором вариантов — управляется
СХЕМОЙ ПОЛЕЙ, отдельной от структуры БД:

- Схема хранится per-`type_code` (не per-категория) в generic key/value
  `settings`-сторе под ключом `field_schemas` (не отдельная SQL-таблица —
  `server/repositories/settings.repo.js::getFieldSchema/setFieldSchema`).
- Формат одной схемы — массив объектов:
  ```json
  [
    { "key": "ip", "type": "ip", "required": false },
    { "key": "network", "type": "select", "options": ["LAN", "WiFi"], "label": "Тип сети" }
  ]
  ```
  `key` — один из `META_KEYS`. `type` — `text` \| `number` \| `select` \|
  `boolean` \| `ip` \| `date`. `label`/`options`/`required` опциональны;
  `options` обязателен и непустой, если `type = select` (проверяется
  Zod-схемой `fieldSchemaEntrySchema`, `server/validation/schemas.js`).
- **Если для `type_code` схема НЕ задана** — используется старый
  дефолтный список по КАТЕГОРИИ (объект `META_FIELDS` в
  `public/js/meta-fields.js`, только на фронте, все поля рендерятся как
  `text`). Это единственный источник обратной совместимости для типов,
  которым ещё не настроили схему — сервер НЕ дублирует этот дефолтный
  список у себя (см. комментарий в `assets.repo.js::_validateMetaAgainstSchema`
  про то, почему это осознанное решение).
- Резолв "имя типа (значение `assets.type`) → `type_code`" — по точному
  совпадению имени со справочником `type_codes.name` (см.
  `_resolveTypeCode()` на сервере / `_resolveTypeCodeByName()` на фронте).
  Если совпадения нет — схема не применяется, действует дефолт.

**Обновлено PROD-5:** миграция физического хранения (`ALTER TABLE`) для
добавления НОВОГО ключа (`warranty`) оказалась дешевле и безопаснее, чем
казалось раньше — реальный прецедент есть (`can_view_accounts`), паттерн
идемпотентен и не требует даунтайма. Если понадобится ещё один ключ вне
исходных 14 — это уже не "инвазивная задача", а известный, проверенный
шаг: PRAGMA table_info + условный ALTER TABLE + добавление в `META_KEYS`.
Что по-прежнему НЕ сделано — переход от фиксированного (пусть и
расширяемого по одному) набора колонок к полностью произвольным ключам
без изменения схемы БД вообще (EAV-подход или JSON-колонка) — это
осталась бы отдельная, более крупная архитектурная задача.

## `history` — журнал событий по активу

Одна строка = одно событие (создание/перемещение/списание/импорт/
переназначение/смена статуса). `asset_id` может быть `NULL` для событий,
чей актив с тех пор физически удалён из `assets` (история переживает
удаление актива — используется как аудит-лог, не как foreign-key-строгая
связь: нет `FOREIGN KEY (asset_id) REFERENCES assets(id)`, в отличие от
`asset_photos`, где такая связь ЕСТЬ, с `ON DELETE CASCADE`).

`org_snapshot` — отдельный текстовый снапшот организации на момент
события, независимый от снапшота `org` в самой таблице `assets` (тот
может уже устареть к моменту, когда читают историю).

Индексы: `idx_history_asset_id`, `idx_history_date`.

## `asset_versions` — снапшоты записей (PROD-10)

В отличие от `history` (журнал ДЕЙСТВИЙ — кто/когда/какое событие),
`asset_versions` — журнал СОСТОЯНИЙ: полный JSON-слепок всех полей актива
(включая `meta`) на конкретный момент. `snapshot` — сериализованный
результат `rowToAsset()`/`normalizeAsset()`, тот же формат, что отдаёт API
для одного актива.

Снапшот пишется в ТРЁХ точках (см. `assets.repo.js`):
- `createAsset()` — версия 1, баланс сразу после создания;
- `updateAsset()` — снапшот состояния ДО применения патча (что было,
  прежде чем изменили);
- `retireAsset()` — финальный снапшот перед списанием.

`move`/`bulk-*` НЕ снапшотятся — то же осознанное ограничение, что уже
принято в PROD-7 (см. комментарий там): массовая операция над сотней
активов дала бы сотню версий за секунду, а инлайн-структура записи
истории в этих функциях не даёт единой точки перехвата без дублирования
кода. Задокументировано явно в `assets.repo.js`, не молчаливый пропуск.

`version_no` — счётчик per-`asset_id`, начинается с 1, вычисляется как
`COUNT(*) + 1` внутри той же транзакции, что и сама запись/снапшот —
атомарно, гонки исключены (SQLite транзакции сериализуются).

`FOREIGN KEY (asset_id) REFERENCES assets(id) ON DELETE CASCADE` — как у
`asset_photos`: удаление актива подчищает его версии автоматически.

**Нет функции восстановления (rollback) из версии** — осознанно вне
рамок этой задачи ("снапшот полей при изменении", не "откат к версии").
Восстановление потребовало бы валидации снапшота по актуальной
type-схеме (PROD-1..4 — схема могла измениться с момента снапшота),
отдельного UI для diff/подтверждения и отдельной записи в history —
достаточно большая задача, чтобы быть отдельным пунктом роадмапа, не
довеском к этому.

Индексы: `idx_asset_versions_asset_id`.

## `asset_photos` — метаданные фотографий

Сами байты изображений на диске (`DATA_DIR/attachments/<asset_id>/<id>.<ext>`),
НЕ в БД — см. комментарий в `sqlite.js` про то, почему (раздувание
единственного .sqlite-файла, который целиком читается в память при
бэкапе). `FOREIGN KEY (asset_id) REFERENCES assets(id) ON DELETE CASCADE` —
при удалении актива строки метаданных удаляются автоматически, но файлы на
диске нужно чистить отдельно (см. `server/repositories/photos.repo.js`).

## Справочники (organizations/filials/locations/type_codes/categories)

Все — обычные SQL-таблицы с `id`/`name`/статусом активности (`status` или
аналог), плюс `org_inv_rules` (правила формата инвентарного номера,
`org_id + type_code → format/counter`, композитный PK). `settings` —
generic key/value JSON-стор для всего, что не заслуживает отдельной
таблицы (`categories`, `type_codes`-совместимость, `field_schemas` и
прочие мелкие настройки).

**`locations.responsible_id`/`responsible` (WH-1, Track 13, «держатель
склада»/МОЛ)** — тот же паттерн id+снапшот имени, что уже применяется у
`assets` (org_id/org, filial_id/filial, location_id/location,
responsible_id/responsible), добавлен через `ALTER TABLE` тем же
защищённым паттерном, что `can_view_accounts` (старые базы не ломает).
Ссылка на `employees`, НЕ настоящий FK — целостность проверяется в JS
(`locations.repo.js::_resolveResponsible()`): несуществующий/удалённый
`employeeId` тихо трактуется как «без держателя» (id и имя снапшота
очищаются), не ошибка. Необязательное поле — есть смысл в первую
очередь для локаций `type='warehouse'`, но структурно доступно для
любого типа локации (сервер не ограничивает).

Держатель НЕ влияет на `responsible` конкретных активов автоматически —
единственный эффект на бэкенде: ничего (сервер не подставляет и не
проверяет). Автоподстановка — целиком на фронтенде, в модалках
перемещения (`asset-tab.js::_wireWarehouseAutoFill()`, переиспользуется
и одиночным, и массовым перемещением): при выборе локации с
`type==='warehouse'` и назначенным держателем поле «Ответственный»
предзаполняется его именем, но НЕ перезаписывает уже введённое значение
и остаётся редактируемым — это подсказка, видимая пользователю перед
отправкой, не скрытая магия на сервере (тот же принцип прозрачности,
что и у `target_type_codes` в REL-6: сервер ничего не решает молча за
пользователя).

## `users` / `employees` / `accounts`

`users` — учётки для входа в приложение (роль/PIN/активность), отдельно от
`employees` (сотрудники организации — те, на кого назначают оборудование,
без возможности входа). `accounts` — учётные записи во внешних системах
(не путать ни с тем, ни с другим) — организовано по категориям, с
опциональными логином/паролем, доступ к просмотру которых регулируется
отдельным флагом `can_view_accounts` у пользователя.

## `api_keys` — REST API-ключи (PROD-11)

Ключ = алиас конкретного пользователя (`user_id` — FK на `users`), НЕ
отдельная сущность со своей моделью прав. Наследует роль владельца
целиком при аутентификации через `Authorization: Bearer itak_...`
(`server/middleware/auth.js::_userFromApiKey`) — тот же принцип, что
личный токен в GitHub/GitLab: живёт под аккаунтом, действует от его
имени. Отдельные scoped-права (например «этот ключ — только для чтения»)
осознанно вне рамок MVP — самостоятельная задача на будущее.

`key_hash` — bcrypt (тот же `SALT_ROUNDS = 10`, что у PIN, см.
`server/pin.js`) от ПОЛНОГО сырого ключа. `key_prefix` — первые 12
символов сырого ключа (`itak_` + 7 символов) в ОТКРЫТОМ виде,
индексирован (`idx_api_keys_prefix`) — нужен, чтобы на каждый запрос не
гонять `bcrypt.compareSync` (дорогая синхронная операция) против хеша
КАЖДОГО существующего в системе ключа; префикс сужает кандидатов почти
всегда до 0-1 строки. Раскрытие 12 символов не ослабляет секрет —
энтропия оставшихся ~32 случайных байт не снижается атакующим, знающим
только префикс.

Сырое значение ключа возвращается ОДИН РАЗ, в ответе на создание —
дальше в системе не хранится и не может быть получено повторно
(write-only, тот же принцип, что у пароля пользователя и у секретов
PROD-7). Утеря ключа = только отзыв (`revoked = 1`) и создание нового.

`FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE` — удаление
пользователя автоматически подчищает его ключи.

Индексы: `idx_api_keys_user_id`, `idx_api_keys_prefix`.

## `asset_relations` — универсальные связи между активами (составные активы)

Не путать с `asset_versions` (снапшоты состояний) и `history` (журнал
действий) — это ТРЕТЬЯ, отдельная сущность: связи МЕЖДУ РАЗНЫМИ активами
(«системный блок содержит эту видеокарту»).

**Почему универсальная таблица, а не (а) meta-поле со ссылкой на другой
актив, или (б) отдельная bespoke-таблица под каждый новый тип связи** —
решалось явно, с пользователем, с прицелом на возможную будущую миграцию
с SQLite на Postgres/MySQL при росте системы:

- (а) meta-поле не даёт FK/UNIQUE на уровне БД (только проверка в JS —
  висящие ссылки копятся тихо), не поддерживает «несколько компонентов
  одного типа» (2 диска) без костылей с ключами `disk_1`/`disk_2`, и
  выбрасывается целиком при миграции на нормальную БД — придётся
  строить настоящую таблицу с нуля ПЛЮС чистить накопившийся мусор из
  битых ссылок.
- (б) N почти одинаковых bespoke-таблиц под каждый новый тип связи
  (сначала «компонент», потом появится «заменён на» — и так далее)
  плодят дублирующуюся инфраструктуру без явной необходимости.
- Универсальная `asset_relations(from_asset_id, to_asset_id,
  relation_type, ...)` — стандартная relational-схема, переносится в
  Postgres/MySQL БЕЗ ИЗМЕНЕНИЙ: одинаковый синтаксис DDL/JOIN в SQLite и
  в любой другой реляционной БД. Это ровно то свойство, которое нужно
  от таблицы, которой предстоит пережить возможный переезд с SQLite —
  см. также обсуждение `node:sqlite`'s `DatabaseSync` (полностью
  синхронный API) как более вероятного, более раннего триггера для
  архитектурных решений, чем «SQLite не тянет объём данных».

```sql
CREATE TABLE asset_relations (
  id TEXT PRIMARY KEY, from_asset_id TEXT NOT NULL, to_asset_id TEXT NOT NULL,
  relation_type TEXT NOT NULL, slot_label TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL, created_by TEXT NOT NULL DEFAULT '',
  FOREIGN KEY (from_asset_id) REFERENCES assets(id) ON DELETE CASCADE,
  FOREIGN KEY (to_asset_id)   REFERENCES assets(id) ON DELETE CASCADE
);
```

**`relation_type`** — ОТКРЫТЫЙ список, не SQL CHECK/enum: белый список
живёт в коде (`relations.repo.js::SUPPORTED_RELATION_TYPES`), тот же
паттерн, что `SUPPORTED_EVENTS` в `notify.js` (PROD-7). Сейчас
единственный тип — `component_of`. Новый тип связи = осознанное решение
разработчика (плюс явное решение по кардинальности для него), не
автоматическое расширение через UI.

**Кардинальность НЕ универсальна для всей таблицы** — специфична для
каждого `relation_type` отдельно (`relations.repo.js::CARDINALITY`). Для
`component_of` физический смысл требует «один компонент — максимум один
родитель одновременно» — обеспечено ДВУМЯ независимыми уровнями защиты:
понятная ошибка в JS ДО обращения к БД, и частичный `UNIQUE`-индекс
`idx_asset_relations_component_unique ON asset_relations(to_asset_id)
WHERE relation_type = 'component_of'` как окончательная гарантия
(partial index — тоже стандартный SQL, есть и в SQLite, и в Postgres,
и в MySQL 8+, переносится без изменений). Будущие типы связи со связью
многие-ко-многим просто не получат такого индекса при добавлении.

**Циклы** — только прямая защита (A→B и B→A одновременно того же
`relation_type` отклоняется). Глубокая защита от цикла произвольной
длины НЕ реализована осознанно — нет сценария вложенной композиции
(компоненты в этой предметной области не имеют своих компонентов).

**Списание актива с активными связями НЕ блокируется и НЕ каскадит** —
связь остаётся как историческая запись («этот диск был установлен в
списанном системнике» — данные, не мусор для автоудаления).

**История**: привязка/отвязка пишет `action_type: 'relation_add'` /
`'relation_remove'` в `history` СИММЕТРИЧНО обеим сторонам связи (по
записи на каждый `asset_id`, а не одну на само событие) — симметрично
`move`/`status_change`.

`FOREIGN KEY ... ON DELETE CASCADE` — как у `asset_photos`/`asset_versions`:
физическое удаление строки `assets` (крайне редкий путь — обычный UI
только списывает, не удаляет) подчищает её связи автоматически.

Индексы: `idx_asset_relations_from`, `idx_asset_relations_to`,
`idx_asset_relations_component_unique` (частичный, см. выше).

### `component_slots` (REL-6) — конфигурация слотов, НЕ таблица

Не SQL-таблица, а settings key/value запись (`getSetting`/`setSetting`,
ключ `component_slots`) — тот же подход, что `field_schemas`/
`notify_config`: `{ [type_code]: [{ slot_label, target_type_codes }] }`.

Осознанно ОТДЕЛЬНО от `field_schemas`/`META_KEYS` (PROD-1..4): каждый
ключ там — реальная SQL-колонка `meta_<key>` в `assets`, а слоты
компонентов ничего не пишут в `meta_*` вообще — значение живёт в
`asset_relations` выше. Фиктивный META_KEY, который никогда не пишется
в свою колонку, либо мусорит схему БД, либо требует специально
обрабатывать этот тип поля везде, где `createAsset`/`updateAsset`
перебирают `meta` — больше риска для отлаженной системы, чем отдельный
маленький settings-ключ рядом.

`target_type_codes` — МЯГКАЯ подсказка для UI-пикера (какие типы
предлагать в этом слоте на карточке актива), НЕ проверяется на сервере
при создании связи — `relations.repo.js::createRelation` ничего не
знает о слотах. Это не пробел в целостности: кардинальность и защита от
циклов (описаны выше) работают независимо от того, настроены ли слоты
для типа вообще.

## Примечание про индексы (PROD-16)

`idx_assets_status`, `idx_assets_org_id`, `idx_history_asset_id`,
`idx_history_date` существуют, но по факту НЕ используются реальными
запросами: `assets.repo.js::selectActive` и `history.repo.js` делают
`SELECT *` без `WHERE` по этим колонкам — вся фильтрация (по org/filial/
status/serial и т.д.) происходит в JS после полной загрузки таблицы в
память, единообразно во всех местах кода (поиск, фильтры списка, дедуп
серийников при CSV-импорте). При текущем масштабе (self-hosted трекер
для одной организации) это не проблема производительности — SQLite читает
даже десятки тысяч строк за миллисекунды. Индексы не мешают, но и не дают
сейчас никакого выигрыша; если архитектуру когда-нибудь переведут на
SQL-side фильтрацию (`WHERE org_id = ?` и т.п.), они уже на месте.
