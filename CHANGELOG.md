## [beta-1-26w39-04]

### Added
- **Audit log** — общесистемный журнал действий (`audit_log` /
  `server/repositories/audit.repo.js` / `GET /api/audit`, только
  `requireAdmin`). Не путать с `history` — та про перемещения/версии
  конкретных активов, эта — про действия пользователей и системы:
  вход/неудачный вход, управление API-ключами, изменение LDAP-конфига,
  смена роли пользователя, restore из бэкапа. Перенесено по мотивам
  аналогичного модуля из Procure-IT (соседний проект той же команды),
  адаптировано под конвенции it-assets: `node:sqlite` вместо `sql.js`,
  `uuidv7` вместо инкрементных id, `repositories/routes`-паттерн вместо
  монолитных роутов, `requireAdmin` вместо `operatorOrAdmin`. Попутно
  унаследована защита, добавленная на Procure-IT уже как фикс: `limit`
  в `listAudit` сразу зажат в диапазон 1–500 (здесь заложено с нуля,
  не отдельным поздним патчем).
  - Точки логирования встроены вручную, по одной, с чтением текущего
    поведения перед правкой (auth-флоу it-assets — заголовки
    `x-user-id`/`x-edit-password`, нестандартный по сравнению с
    Procure-IT, где перенос делался вслепую по плану было бы рискованно):
    - **Вход/неудачный вход** — в оба реальных роута логина
      (`POST /api/users/auth` — PIN, `POST /api/users/login` —
      логин/пароль + LDAP-фоллбэк), а не в `requireAuth` — тот
      выполняется на КАЖДЫЙ авторизованный запрос, логирование там
      залило бы `audit_log` шумом вместо фиксации собственно факта входа.
    - **Смена роли** — отдельного роута нет, роль правится через общий
      `PUT /api/users/:id`; `user.role_change` пишется только когда
      `role` реально пришла в теле запроса и отличается от текущей
      (сверка через `db.getUser()` до `db.updateUser()`).
    - **LDAP-конфиг** (`PUT /api/settings/ldap-config`) — в `detail`
      только имена изменившихся полей (`fields_changed`), НЕ значения:
      `bind_password` не должен попадать в лог ни в открытом, ни в
      замаскированном виде.
    - **Restore из бэкапа** (`POST /api/backup/restore/:name`) —
      запись пишется ДО `makeBackup('pre-restore')`/распаковки, не
      после: если архив содержит `it-assets.sqlite`, файл на диске
      полностью заменяется при restore, и запись «после» была бы
      потеряна вместе с остальным текущим содержимым `audit_log`.
  - 16 новых тестов (`tests/audit-log.test.js`): unit на
    `logAction`/`listAudit` (включая фильтры, сортировку по `ts DESC`,
    зажатие `limit`, `actor: null`), права доступа `GET /api/audit`
    (401/403/200), и по каждой точке интеграции — что она реально
    пишет (включая негативный случай: `PUT /api/users/:id` без поля
    `role` НЕ создаёт запись `user.role_change`).
  - Фронтенд (страница просмотра лога) НЕ сделан — следующий шаг,
    отдельная задача по образцу `history`-вкладки в
    `public/js/views/`.

## [beta-1-26w39-03]

### Added
- **`scripts/bump-version.js`** — автоматический расчёт следующей версии
  по ISO-неделе, вместо ручного вычисления недели в уме перед каждой
  сборкой. `npm run bump-version` = `bump-version.js` + `sync-version.js`
  одной командой.
  - Та же ISO-неделя, что уже в `VERSION` — счётчик `NN` просто `+1`.
    Неделя сменилась — счётчик сбрасывается на `01`, подставляется
    новая неделя.
  - Намеренно ОТДЕЛЬНО от `sync-version.js`: тот — чистая пропагация уже
    готовой строки версии по файлам, без обращения к дате, идемпотентен
    (два прогона подряд без изменения `VERSION` дают одинаковый
    результат везде). Если бы `sync-version.js` сам считал неделю по
    текущей дате при каждом запуске — два прогона в разные дни без
    реального релиза давали бы РАЗНЫЙ результат, версия перестала бы
    быть детерминированной.
  - ISO-8601 неделя (не наивный `getMonth()`/`getDate()`) — недели с
    понедельника, неделя 1 года — та, что содержит первый четверг года;
    единственный способ, не ломающийся на границе года (29 декабря
    2025 — уже неделя 1 2026-го). **Реальный баг, пойманный живым
    тестом при разработке**: первая версия регулярного выражения
    `VERSION_RE` разбивала неделю на ДВЕ отдельные capture-группы
    (`(\d{2})w(\d{2})`), а код деструктурировал результат как ОДНУ
    (`[, stage, n, prevWeekKey, prevSeq] = m`) — из-за сдвига индексов
    `prevWeekKey`/`prevSeq` получали не те группы, и повторный запуск
    в тот же день молча возвращал ТУ ЖЕ версию вместо инкремента.
    Исправлено (регулярка приведена к единой группе недели, как в
    `sync-version.js`) и закреплено тестами именно на этот сценарий
    (повторный вызов в тот же день).
  - Не дублирует `tools/release/release.sh` (берёт версию явным
    аргументом, делает полный релизный флоу — merge/tag/push) — этот
    скрипт для повседневных dev-сборок.
  - 14 новых тестов (`tests/bump-version.test.js`): граничные ISO-даты
    (переход года в обе стороны, 53-недельный год, сверено с Python
    `date.isocalendar()`), инкремент/сброс счётчика, отсутствующая/
    битая текущая версия, `--stage`/`--n` оверрайды.

## [beta-1-26w38-12]

### Added
- **ARCH**: составные активы — универсальные связи между активами
  (`asset_relations`). Проработано отдельно с пользователем: сравнение
  трёх подходов (meta-поле со ссылкой / bespoke-таблица под каждый тип
  связи / универсальная таблица связей) с явным прицелом на возможную
  будущую миграцию с SQLite на Postgres/MySQL при росте системы —
  универсальная таблица выбрана как единственная, что переносится без
  изменений (стандартный SQL, тот же синтаксис везде). Полное
  обоснование — в `SCHEMA.md`.
  - Новая таблица `asset_relations` (`from_asset_id`, `to_asset_id`,
    `relation_type`, `slot_label`). `relation_type` — открытый белый
    список в коде (`relations.repo.js::SUPPORTED_RELATION_TYPES`), тот
    же паттерн, что `SUPPORTED_EVENTS` у PROD-7. Сейчас один тип:
    `component_of`.
  - Кардинальность специфична ДЛЯ ТИПА связи, не для таблицы целиком:
    `component_of` — «один компонент, максимум один родитель
    одновременно», два независимых уровня защиты (понятная JS-ошибка +
    частичный `UNIQUE`-индекс в БД как окончательная гарантия —
    `WHERE relation_type = 'component_of'`, тоже стандартный,
    переносимый SQL).
  - Прямой цикл (B→A при уже существующем A→B того же типа) отклоняется.
    Глубокая защита произвольной длины — осознанно вне рамок (нет
    сценария вложенной композиции в этой предметной области).
  - Списание актива с активными связями НЕ блокируется и НЕ каскадит —
    связь остаётся как историческая запись.
  - Привязка/отвязка симметрично пишет `relation_add`/`relation_remove`
    в историю ОБОИХ активов (по записи на каждую сторону).
  - `GET /api/assets/:id/relations`, `POST/DELETE /api/asset-relations`
    (`requireAuth` на запись, `requireLogin` на чтение).
  - UI: блок «🔗 Компоненты и связи» на карточке актива — список связей
    в обе стороны (я владею / я сам чей-то компонент), живой поиск
    активов для привязки (переиспользует существующий
    `/api/assets/search`), слот-метка через `prompt()` (сознательно не
    отдельная модалка ради одного необязательного текстового поля).
  - 22 новых теста (`tests/asset-relations.test.js`): полное покрытие
    кардинальности, защиты от цикла, симметричной истории, отсутствия
    каскада при списании, обеих сторон в `GET .../relations`.
  - **Известное ограничение (осознанно, не для этого раунда)**: интеграция
    с системой типизированных полей (PROD-1..4) — чтобы админ мог
    ограничить «у Системного блока слот „Видеокарта" принимает только
    активы типа GPU» — не сделана. Сейчас любой актив можно привязать к
    любому как `component_of`, без проверки типов. Мягкое ограничение
    UX, не пробел в безопасности — можно добавить отдельным шагом при
    необходимости.

## [beta-1-26w38-11]

### Added
- **IDEA-3**: «Инвентаризация по месту» — новая вкладка «🔍 Инвентаризация»
  в главной навигации. Оператор выбирает место, сканирует активы
  (физическим сканером — keyboard-emulation + Enter, тот же паттерн, что
  у `/scan.html`, PROD-8), список накапливается на фронтенде (без
  серверной сессии — проще и безопаснее: не остаётся «зависшей»
  незавершённой сессии инвентаризации в БД, если вкладку закрыли на
  середине обхода), одним запросом сверяется с учётом.
  - `POST /api/assets/inventory-check` (`requireAuth`) —
    `assetsRepo.checkInventoryByLocation()`. Только ОТЧЁТ о
    расхождениях, ничего не мутирует: `missing` (числится тут, не
    отсканировано), `unexpected` (отсканировано, но числится в другом
    месте — с `actual_location`), `unknown` (код не найден в системе
    вообще). Поиск кодов — та же логика, что у `/api/public/scan`

  необработанное исключение — вообще без единого лога о причине. Источники
  предлагали противоположные философии (net-monitor: логировать и
  продолжать оба случая; procure-it: завершаться после обоих, следуя

  обходится почти бесплатно. Логика проверена изолированным тестом с тем
  же кодом обработчиков: `unhandledRejection` подтверждённо не завершает

  `SIGTERM`/`SIGINT` → штатное закрытие БД → чистый выход, без SIGKILL,
